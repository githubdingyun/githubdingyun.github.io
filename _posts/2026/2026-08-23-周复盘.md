## 4. 四大护栏的落地形态：在 sdd-harness 里各自对应什么

这是本周最重要的「对账表」——纸面上的四大护栏，在本周实操对象里的实体是什么：

| 护栏（Day 8） | sdd-harness 落地形态（Day 9–13 实测/精读） | 你亲手接触过吗 |
|---|---|---|
| 项目规则（CLAUDE.md+Skills） | 根目录 `CLAUDE.md`/`AGENTS.md` 5 行指针 → 重定向到 `.ai/ROUTING.md`（canonical 唯一入口）；PRODUCT/CONTEXT/BACKLOG 用户填写 | □ 精读（Day 9） |
| 前置规划与权限（Plan Mode+Permission） | 本讲义标「待核验」：sdd-harness 以文件规则约束流程；权限分级属于 AI 工具侧能力，harness 是否内置权限机制以 README 为准 | □ 未直接接触 |
| 事后验证（Hooks） | `hooks/pre-commit-spec-check.sh`（拦截：feat/feature 分支改代码不碰 spec/ADR → 拒；chore/docs/fix/hotfix 豁免）+ `hooks/post-edit-trace.sh`（记录：打印本次提交涉及的 spec/ADR/代码） | □ 实操（Day 10/13） |
| 上下文隔离（Subagents） | `.ai/agents/`（如 spec-writer 子代理）——把「写 spec」这类职责隔离给专门代理 | □ 精读（Day 9） |

> 复盘问题一：**哪个护栏你最有实感？** 大概率是 Hooks——因为你被它拦过。这正说明：机制只有「拦住过你一次」，你才会真正相信它不是摆设。

## 5. 我的 Harness 理解图

先给你一张参考图（基于本周已核验素材），然后**画出你自己的**——允许不一样，画得越「你的」越好。

### 5.1 参考图（ASCII 版）

```
            ┌────────────────────────────────────────────┐
            │           你的仓库（Git，零依赖）              │
            │                                            │
  AI 进来 → │  CLAUDE.md / AGENTS.md（5 行指针）           │
            │      │ 重定向                                │
            │      ▼                                      │
            │  .ai/ROUTING.md（canonical 唯一入口）        │
            │      │                                      │
            │      ├── 事实输入：PRODUCT / CONTEXT / BACKLOG│
            │      ├── 决策历史：adrs/（ADR 0008）          │
            │      ├── 流程：commands/（七命令，让 AI 遵循） │
            │      ├── 守门：hooks/（pre-commit 拦 +        │
            │      │             post-commit 记）           │
            │      ├── 隔离：agents/（spec-writer 等）      │
            │      └── 契约：specs/（spec v2 住这里）       │
            │                                            │
            └────────────────────────────────────────────┘
  开发循环：spec → story → implement → verify → review → release → phase-close
  守门规则：feat/* 改代码不碰 specs|adrs → 拦；fix/* 等豁免；SH_SDD_SKIP=1 显式例外
```

### 5.2 画出你自己的图

要求（三条，都满足才算合格）：

1. **必须包含**：AI（运行时）、`.ai/`、ROUTING、commands、hooks、specs、spec v2 七样东西；
2. **必须体现关系**：至少一条「流程」箭头（如 spec→implement）和一条「守门」箭头（如 commit→pre-commit）；
3. **必须体现本周的实操痕迹**：在图上标注「Day 10 被拦」「Day 13 三态」这类你真实经历过的点。

可以用 ASCII、Mermaid，或者手画拍照。**画图的过程比图本身重要**——画不出来就回去翻 Day 9 第 4 节。

## 6. 写第二篇学习笔记（20 分钟，≥500 字）

按研究式学习三件套，模板如下：

```
# Week 2 周复盘（Day 8–14）

## 一、预期（我以为）
学这周之前，我以为 harness 是……（写 1–2 句，越具体越好）

## 二、观测（实际发生）
- 我亲手装上了：□ bootstrap.sh  □ clone + install.sh（或写实际方式）
- 我亲眼看到/亲手制造的拦截次数：______ 次；豁免/例外各 ______ 次
- 我的 spec v2 是否进入了 .ai/specs/：□ 是 □ 否（原因：______）
- 三态结果：放行 □ 拦截 □ SH_SDD_SKIP □（Day 13 记录）
- 我最意外的发现：______（例：hook 其实不检查 spec 质量，只检查「有没有碰 spec」）

## 三、复盘（新认知）
- 本周最大的认知：______
- 它推翻/强化了我 Week 1 的什么想法：______
- Week 3 学工程化闭环时我要带着的问题：______

## 四、下周行动
- 我要把 Day 13 的 spec v2 用到哪里：______
- 我要不要调整我的 spec 写法（因为 hook 只认「存在」，质量靠 review）：______
```

> 提示：第 6 节模板里有个重要发现值得写——**hook 只守「有没有 spec」，不守「spec 好不好」**。质量责任回到了人/review 环节。这个边界，是 Week 2 给你最大的认知增量之一。
