## 3. 完整学习路径：Day 1–28 一句话回顾

| 阶段 | 天数 | 一句话 |
|---|---|---|
| 认知打底 | Day 1–7 | 搞懂为什么需要工程化、合格 spec 长什么样，亲手写出 spec v2 |
| Harness 工程 | Day 8–14 | 四大护栏、.ai/ 目录、pre-commit hook、七命令循环，跑通 spec-first |
| 工程化闭环 | Day 15–21 | 四类契约、规范即代码/测试、持续交付门禁，端到端交付证据 |
| 沉淀输出 | Day 22–28 | 模板化（spec 模板）→ 工具化（commands/config.sh）→ 流程化（团队规范）→ 验证化（大作业四件套）→ 分享化（今天） |

> 四大护栏（Day 8）贯穿始终：规则（CLAUDE.md+Skills）、权限（Plan Mode+Permission）、验证（Hooks）、隔离（Subagents）——你四周做的所有事，都是在把这四道护栏落地成自己项目的配置。

## 4. 交付物一：spec 模板最终版（v3）

把 Day 22 的 v1、Day 27 的 v2 合并，产出 v3：

- **主体** = 七要素 + GWT 验收 + 四类契约 + 变更记录（delta 四标记）
- **新增** = v2 迭代出的"错误码清单""基线来源""行为契约必填"等
- **文件头**加版本号与变更记录：

```markdown
# MySpec-Template v3（最终版）

## 变更记录
- v1（Day 22）：初版，融合七要素 + delta spec + 四类契约
- v2（Day 27）：大作业复盘后补 <错误码清单 / 基线来源 / ...>
- v3（Day 28）：定稿，删除无用占位，统一术语（spec 模板 / delta spec / GWT）
```

## 5. 交付物二：harness 配置清单

```markdown
# My Harness 配置清单（<项目名>）

## 安装
- 来源：sdd-harness（github.com/iMark21/sdd-harness）
- 安装命令：curl -sSL https://raw.githubusercontent.com/iMark21/sdd-harness/main/bootstrap.sh | bash -s -- --stack <stack>
- stack 选择：<python/swift/android/node/go/rust/generic>

## .ai/ 目录（Day 22）
- 保留：ROUTING / CONTEXT / BACKLOG / adrs / commands / hooks / notes / specs
- 裁剪：____

## commands（Day 23）
- 已固化：spec / verify / review / ____

## hooks / config.sh（Day 23）
- SH_CODE_GLOBS：<默认 * / 自定义>
- SH_CODE_EXCLUDE_GLOBS：<.ai/*、*.md、docs/* …>
- 分支豁免：feat/* 查 spec；chore/docs/fix/hotfix 豁免

## 流程规范（Day 24）
- 分支：develop 切 feat/<short-description>；main 只发布
- merge：squash merge；release/vX.Y.Z → tag → back-merge；SemVer
```

> 这份清单本身就是"新项目三分钟搭架子"的检查表——复制一份，改掉尖括号，就是下一个项目的配置。

## 6. 交付物三：踩坑清单

每条三栏：**坑 → 表象 → 解法**。至少 5 条，示例：

| # | 坑 | 表象 | 解法 |
|---|---|---|---|
| 1 | spec 里写"快" | AI 自己定义 3s 算快 | 一律 GWT + 数字 + 基线（Day 5/7） |
| 2 | 非目标写太少 | AI"顺手"加了功能 | 非目标 ≥3 条，含"我顺手的念头"（Day 5） |
| 3 | config.sh 排太宽 | 真代码被排除，hook 不拦 | EXCLUDE 只放 .ai/ 与文档类（Day 23） |
| 4 | chore 分支干 feat 的活 | 规避 spec 检查 | 分支名 = 意图，hook 只看名字（Day 24） |
| 5 | 口头 review | 事后说不清谁看的 | 书面审查记录，无记录不 merge（Day 25） |
| 6 | SH_SDD_SKIP 随手用 | 门禁形同虚设 | 显式例外必须留痕，且复盘时解释（Day 13） |

> 把你 Day 1–27 的"卡住瞬间"全部翻出来，挑最痛 5–10 条填进这张表。

## 7. 交付物四：内部分享稿骨架

```markdown
# 内部分享：AI 编程怎么从"能跑"到"可控"

## 开场（2 分钟）
- 痛点：出码率 90% 却没提效（三大瓶颈）
- 一句话主张：AI 编程要从"个人技能"升级为"团队级工程能力"

## 主线（10 分钟）
1. 认知：SDD（想什么）+ Harness（怎么做）的分工
2. 工具：spec 模板 + .ai/ 目录 + commands + hooks（现场演示一次 pre-commit 拦截）
3. 流程：分支规范 + 书面审查 + 合并前自动检查
4. 证据：放 Day 26 大作业的交付四件套（spec / 代码 / 验证证据 / review 记录）

## 演示（5 分钟）
- 现场演示：3 行需求 → spec 模板 → hook 拦截 → 补 spec 放行

## 收尾（3 分钟）
- 给团队的三个最小动作：① 建 .ai/ ② 装 hook ③ 定分支规范
- 附：四件套文件（模板 / 配置清单 / 踩坑清单 / 本稿）
```

> 关键：**"证据"部分必须放你 Day 26 的真实交付物**，讲自己踩过的坑，比讲别人的案例有说服力得多。

## 8. 动手练（收尾时间盒，约 60–80 分钟）

1. **定稿模板**：合并 v1 + v2 → `MySpec-Template-v3.md`，按第 4 节格式写变更记录（20 分钟）
2. **配置清单**：按第 5 节模板填你的真实配置（15 分钟）
3. **踩坑清单**：按第 6 节填 ≥5 条（15 分钟）
4. **分享稿**：按第 7 节骨架写 300–500 字大纲（20 分钟）
5. **归档**：四件套放一个目录（如 `Week4-沉淀输出/` 或你的 `.ai/notes/` 下），并在 ROUTING.md 登记
6. **收官打卡**：评估标准 6 条逐条自检——能打勾的说明你毕业了
